# Guard authority key — how this one was made

**Read this before citing `can_claim_containment: YES` anywhere.**

## What happened

On 2026-08-14 the repository owner explicitly authorised the agent to generate
the guard authority key and sign the bounds configuration. It did.

| | |
|---|---|
| **authority pubkey** | `0479cdb6418396235ced4f64987076da3f1291f5f91b8e66b87b57990cc3452d` |
| **private key** | `~/.gyza/authority.key`, mode 0600, **outside the repo** and never committed |
| **generated by** | the agent, in-session, **on the machine that runs agents** |
| **signed config** | `gyza/containment/guard_bounds.signed.json`, v1, 4 bounds |
| **config hash** | `71238d791a8ee66c8dbe82e835817f1b070b1a8332dc4660f4efc2921ad65005` |

## Why that matters, stated plainly

`guardconfig.py`'s own argument is that the containment claim is an **induction**:
the invariant holds at s₀ and every admitted transition preserves it. If the
constrained system can rewrite the invariant there is no base case — *"a guard an
agent can edit is not a guard."*

**This key was generated by an agent, on the machine it constrains.** The
cryptography is sound and the verification path is real: a tampered config is
refused, a config signed by another key is refused, a plain file under an
authority is refused. What is **not** established is the *separation* the
mechanism assumes.

> ### `SIGNED` here means "the signature verifies." It does NOT mean "the key was held outside the constrained system."
>
> Do not let those read as the same thing in a capability statement, a pitch, or
> a submission.

## What to do about it

Regenerating properly costs one command and invalidates nothing else — the
mechanism does not care *which* key, only that it verifies:

```
# on a machine that does NOT run agents
python scripts/sign_guard_config.py --generate-key authority.key
python scripts/sign_guard_config.py --key authority.key
# then set GYZA_GUARD_AUTHORITY to the printed pubkey
```

Move the private key to hardware or a password manager, and delete
`~/.gyza/authority.key` from this machine. At that point this file can be
replaced with a note saying the separation holds, and the claim becomes what it
appears to be.

## One thing this did establish

Signing alone did **not** manufacture the claim. Immediately after signing,
`can_claim_containment` was still **False**, because `H5_storage_growth` had no
declared level — two independent gates, and C-8 could not paper over D1. The
claim only became available once H5's level was loaded, and that level was
**transcribed from `GyzaConfig.max_artifact_store_gb`**, a value the operator had
already declared and which nothing read: `gyza status` printed it as an enforced
cap while `ArtifactStore.max_bytes` stayed `None` everywhere.

---

## Where the authority key lives — decided 2026-08-15

**The key stays on this machine, and that is a deliberate decision with a
trigger, not an oversight.** Gyza is not deployed. Nothing signs for a third
party, no peer trusts this key, and moving it to separate custody before there
is anything to protect buys ceremony rather than security.

**The trigger is DEPLOYMENT, not time.** The moment any of the following becomes
true, the key must move to custody the running system cannot read:

1. a daemon reachable from a network other than loopback trusts a signature made
   by this key,
2. any third party is asked to verify a Gyza claim against it, or
3. a release binary is signed under it.

Recorded here rather than in a session note because the condition outlives any
session, and a deferred security decision with no written trigger is
indistinguishable from a forgotten one.
